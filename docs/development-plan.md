# v0.1 开发计划

更新日期：2026-09-01

状态：已确认

## 执行原则

- v0.1 分批开发，每次只执行一个批次。
- 每批必须形成可独立运行和验收的结果，不提前混入下一批功能。
- 每批结束后检查运行结果、测试、截图和变更范围，再决定是否调整后续计划。
- 当前批次通过后才进入下一批，避免架构、布局或交互问题扩散。
- AI、暗色模式、备孕、易孕期等非 v0.1 功能不得作为“顺便实现”的内容加入。

## 批次 0：工程基线

### 范围

- 初始化 Expo + React Native + TypeScript 项目。
- 配置 Expo Router、Restyle、代码检查、格式化和测试框架。
- 验证 SQLite、日历、SVG、动画、手势和底部面板候选依赖的版本兼容性。
- 确认 Expo Go 或 Development Build 的开发方式。
- 建立与领域、数据和页面边界一致的目录结构。

### 验收

- iOS 和 Android 配置可被 Expo 工具识别。
- TypeScript、Lint 和测试命令通过。
- 候选原生依赖通过 Expo 依赖检查。
- 项目只包含应用外壳，不包含后续批次业务实现。

## 批次 1.5：Soft Companion 视觉验证

状态：已完成并通过验收，结果参见 [批次 1.5 Soft Companion 视觉验证结果](./batch-1.5-result.md)。

建议分支：`batch/1.5-soft-companion-visual-validation`

### 目标

用当前 Expo + React Native + Restyle 技术栈验证 `Sorbet + Cashmere + Soft Pouf` 组合能否形成适合成年女性长期使用的 `Soft Companion` 视觉，而不是提前完成全 App 换肤。

视觉比例保持为 70% 成熟清晰、20% 柔软黏土触感、10% 克制插画与微动画。本批次核心页面不强制加入插画，10% 插画层留给后续首次引导、空状态和完成反馈验证。

### 唯一允许改造的界面

- `记录` 页：月历、所选日期摘要和记录项目列表。
- 一个记录详情底部面板：优先选择能覆盖选中、未选中和多选状态的 `症状` 面板。
- 底部导航：`今天`、`记录`、`趋势` 三个入口及其选中、未选中状态。

今天页、趋势页、设置页、首次设置流程及其他记录面板不得在本批次顺带改造。共享组件只有在上述三个验证目标直接使用时才允许调整。

### 视觉验证内容

- `Sorbet`：负责日历的柔和状态色、轻盈层次和清楚的日期选择反馈。
- `Cashmere`：负责温暖中性色、成年化的信息层级、中文排版和克制留白。
- `Soft Pouf`：只用于记录选项、主要动作和导航选中态的局部按压感，不给整页和每个容器添加厚阴影。
- 建立实验性的语义颜色、圆角、阴影、描边和动效令牌；令牌名称表达用途，不绑定外部主题名称。
- 验证单一图标语言；通用图标优先评估 Phosphor，月经领域图标使用项目自有 SVG 草案。本批次不进行全项目图标迁移。
- 动效仅用于按下、选中和面板出现等状态变化，并为系统减少动态效果设置提供降级。

### 数据与架构边界

- 继续使用批次 1 的固定模拟数据和组件内存状态，刷新后允许重置。
- 不新增或修改 SQLite、Drizzle、Repository、数据库迁移、领域模型、预测算法或持久化状态。
- 不改变记录字段、保存语义、日期规则和页面间数据契约。
- 不引入 WebView、Capacitor 或 shadcn 运行时代码；外部 Registry 只作为视觉参考。

### 真机验证矩阵

- 至少在一台 iPhone 和一台 Android 真机验证；同时覆盖紧凑尺寸和标准尺寸，缺少对应真机时用模拟器补齐尺寸矩阵，但不能替代双平台真机结论。
- 检查顶部与底部安全区、月历文字和状态辨识、44pt/48dp 触控区、长中文文本、底部导航稳定高度及系统字体缩放。
- 检查底部面板拖动、点遮罩关闭、系统返回键、短屏滚动、键盘避让和关闭后的焦点恢复。
- 对比 iOS 与 Android 的阴影、描边、连续圆角和按压反馈，避免一端呈现为脏灰、发糊或过度膨胀。
- 检查正常动效与减少动态效果两种设置，确保无动画时仍能识别状态变化。
- 保存紧凑与标准尺寸、iOS 与 Android、默认与关键交互状态的截图，作为后续页面推广基线。

### 验收与决策

- 三个验证目标使用同一套语义令牌，视觉上形成统一、成年、柔和且清醒的体验。
- 实际经期、当前选择、已有记录、未记录和导航选中态不能只依靠颜色区分。
- 常用记录操作效率不低于批次 1，界面密度和文字可读性不因黏土效果下降。
- `git diff` 中不出现任何数据层、预测或持久化文件变更。
- 真机问题、平台差异和最终截图完成记录，并由用户明确选择“通过”“调整后复验”或“放弃该方向”。
- 只有选择“通过”后，才能把令牌、图标与组件语言推广到今天页、趋势页、设置页、首次设置和各类状态页；推广工作归入后续批次，不在本批次追加。

- 继续使用系统中文字体，周期数字和统计数据使用等宽数字；不新增字体依赖。

### 数据与架构边界

- 继续使用批次 1 的固定模拟数据和组件内存状态。
- 不修改 `src/features`、SQLite、Drizzle、Repository、领域模型、预测算法或持久化状态。
- 不改变记录字段、保存语义、日期规则和页面间数据契约。
- 不引入 WebView、Capacitor、shadcn 运行时代码或新的字体资源。

### 验收

## Git 工作流

每个批次使用独立分支，分支在开发开始前创建：

1. 确认本地 `master` 与远端同步。
2. 从 `master` 创建 `batch/<编号>-<名称>` 分支。
3. 只在该分支实现当前批次。
4. 完成当前批次的测试、检查和人工验收。
5. 提交当前批次并推送分支到远端。
6. 使用非快进合并将批次分支合并到 `master`，保留明确的合并节点。
7. 推送远端 `master`，然后才允许创建下一批分支。

批次分支推送后保留在远端，不自动删除。需要回滚时优先对对应合并提交执行 `git revert`，不改写已经推送的公共历史。未经明确要求不使用强制推送。
